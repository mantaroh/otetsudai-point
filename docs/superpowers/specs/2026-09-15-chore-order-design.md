# お手伝いメニューの並べ替えと追加 設計

親が、お手伝いメニューを親設定から追加できて、並び順も自分で決められるようにする。

今は並び順が使用頻度で自動的に決まり（`use_count DESC`）、追加は台帳の「そのほか」からしかできない。

## 決めたこと

| 項目 | 決定 |
|---|---|
| 並び順 | 親が決めた順に**完全に置き換える**。使用頻度では動かなくなる |
| 並べ替えの操作 | 各行の ↑ ↓ ボタン |
| 新しく足したもの | 親設定から足したものも、子が「そのほか」で足したものも、**一番上** |
| 既存の並び | 移行時に、今の使用頻度順をそのまま初期値にする |

使用頻度順をやめるのは、子どもから見て**毎回同じ位置に同じボタンがある**ほうが使い慣れるため。
今の作りだと、よく押すお手伝いほど上に上がっていくので、ボタンの位置が日によって変わる。

これは DESIGN.md 2.3「並び順は直近の使用頻度順」を覆す判断なので、DESIGN.md も書き換える。

`use_count` は数え続ける。親設定の一覧に「N回」として出ていて、どれがよく使われているかの参考になる。

## データ

`migrations/0006_chore_order.sql`

```sql
ALTER TABLE chores ADD COLUMN sort_order INTEGER NOT NULL DEFAULT 0;

-- 今の並び（使用頻度順）をそのまま初期値にする。
-- ORDER BY は現在の listChores と一字一句同じにすること。ずれると、
-- デプロイした瞬間にお子さんの画面でボタンの並びが変わってしまう。
UPDATE chores SET sort_order = (
  SELECT rn FROM (
    SELECT id, ROW_NUMBER() OVER (
             PARTITION BY family_id
             ORDER BY use_count DESC, last_used_at DESC, name, id
           ) AS rn
      FROM chores
  ) ranked
  WHERE ranked.id = chores.id
);

CREATE INDEX chores_family_sort ON chores (family_id, archived_at, sort_order);
```

`sort_order` は小さいほど上。負の値も使う（下記「一番上に足す」）。

アーカイブ済みの行も採番しておく。アーカイブを戻したときに `sort_order` が 0 のままだと、
意図しない位置に出てくるため。

`(family_id, sort_order)` にユニーク制約は付けない。並べ替えで2行の値を入れ替えるとき、
SQLite は文ごとに制約を確かめるので、途中で一時的に重複して落ちてしまう。
並び順は下記の「全体を送り直す」方式で毎回振り直すので、重複が残り続けることはない。
念のため `ORDER BY sort_order, name` として、万一重複しても表示は決まった順になるようにする。

## 並び順の読み出し

`src/worker/db/chores.ts` の `listChores`：

```sql
ORDER BY sort_order, name
```

子の台帳（bootstrap の `chores`）も、親設定の一覧も、この順で並ぶ。

## 一番上に足す

新しいお手伝いには、その家庭の今の最小値より1小さい値を入れる。

```sql
sort_order = (SELECT COALESCE(MIN(sort_order), 0) - 1 FROM chores WHERE family_id = ?)
```

全体を振り直さずに済むので、追加は1行の書き込みで終わる。

`upsertChoreByName` は、同じ名前が既にあれば新しく作らず既存の行を返す（表記ゆれのマージ）。
このとき：

| 既存の行の状態 | 並び |
|---|---|
| 使われている（アーカイブされていない） | **動かさない**。子が既存のお手伝いの名前を打っただけなので |
| アーカイブ済み | **一番上に戻す**。親から見れば「足し直した」ことになるので |

```sql
ON CONFLICT (family_id, name_norm) DO UPDATE SET
  sort_order  = CASE WHEN archived_at IS NOT NULL THEN excluded.sort_order ELSE sort_order END,
  archived_at = NULL
```

## 並べ替えの API

`PUT /api/chores/order`（親のみ）

```json
{ "choreIds": ["cho_a", "cho_c", "cho_b"] }
```

画面に見えている並びを、そのまま丸ごと送る。サーバは受け取った順に `0, 1, 2, ...` と振り直す。

↑ ↓ を押すたびに、画面側で入れ替えた後の並びを送る。
隣と入れ替える API（`POST /chores/:id/move`）も考えたが、並びを丸ごと送るほうが
「今どう並んでいるか」について画面とサーバの認識がずれない。

### 送られてきた並びが古いときは断る

受け取った `choreIds` が、その家庭の**アーカイブされていないお手伝い全部**と
過不足なく一致しなければ `409` を返す。

親が並べ替えている間に子が「そのほか」で1件足した、というのが一番ありそうなケース。
そのまま振り直すと、足された1件だけ番号が付かずに残る。
画面は `409` を受けたら一覧を読み込み直す。

他の家庭のお手伝いの ID が混ざっていた場合も、同じく一致しないので `409` になる。
「存在しない」と「他の家庭のもの」を区別しない、という既存の方針（`errors.ts`）とも合う。

## テスト

| 層 | 見るもの |
|---|---|
| API結合 | 並べ替えが反映される。古い並びや他家庭の ID は 409。親設定から足すと一番上。「そのほか」で足すと一番上。既存の名前を打っても動かない。アーカイブを戻すと一番上。子の端末からは並べ替えできない |
| 画面 | 追加欄から足せる。↑ ↓ で並びを入れ替えた一覧が API に送られる。端の ↑ ↓ は押せない。409 のとき読み込み直す |
| マイグレーション | 初期値の採番を使い捨ての sqlite で確かめる。今の `listChores` と同じ順になること、アーカイブ済みも採番されること |

## 本番への反映

`0006` は本番の `chores` に列を足して、既存の行に値を書き込む。
前回と同じく **バックアップ → マイグレーション → デプロイ** の順で行う。

マイグレーションを先に流しても、古いコードは `sort_order` を見ないので動き続ける。

## 実装で設計から変えたこと

| 変更 | 理由 |
|---|---|
| 新しい家庭の種のお手伝いに、リストの順で `sort_order` を振る | 全部 0 のままだと同点が名前順で決まり、名前を直しただけでボタンの位置が動いた。テストで見つかった |
| 親設定でアーカイブを戻した場合も一番上へ | 設計では「同じ名前で足し直した場合」だけ書いていた。どちらも親から見れば足し直しなので揃えた。もともとアーカイブされていない行は動かさない |
| 一覧の行のボタンに「〜 を編集」という名前を付けた | 同じ行に ↑ ↓ が並ぶので、3つのボタンがどれも名前で始まり区別できなくなるため |
| `e2e/journey.spec.ts` の `getByLabel("名前")` を `exact: true` に | Playwright の `getByLabel` は既定で部分一致。常に出ている「あたらしいお手伝いの名前」にも当たるようになった |

新しい家庭の最初の並びは、これまでの名前順から種のリストの順（しょっきをあらう、せんたくものをたたむ、おふろそうじ…）に変わる。
既存の家庭はマイグレーションで今の並びをそのまま引き継ぐので、影響しない。
